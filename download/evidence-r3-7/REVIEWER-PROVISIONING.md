# R3-7 — Reviewer Provisioning Model

This is the ONLY path to staging authorization. The workbench has no
self-registration, no shared accounts, and no HTTP provisioning endpoint.

## Identity model

- **Reviewer record** (durable registry, `download/teacher-validation/reviewers.json`,
  0600, OUTSIDE git, path overridable via `TV_REVIEWERS_FILE`):
  `{id: "tvr-xxxxxxxx", name, role: "teacher", tokenHash (sha256), status: active|revoked, epoch, createdAt, revokedAt?, provisionedBy, note?}`.
- **Token**: `tvr_` + 32 random bytes (base64url). Generated by the CLI,
  printed to stdout EXACTLY ONCE, stored ONLY as a SHA-256 hash.
- **Role**: `teacher` is the only issuable role; its ONLY privilege is to
  STAGE intent (VALIDATE/REJECT/FLAG/REVERSE into the hash-chained staging
  log). No role can APPLY anything — canonical apply remains the gated
  importer's exclusive power (operator-side, server-side, unchanged).
- **No shared accounts**: active reviewer names are unique
  (case-insensitive); each reviewer has their own token and id. Attribution
  in the staging log carries BOTH the display name AND the stable
  `reviewerId` (outside the entry hash, F-3 pattern — the frozen hash base
  and the importer's verifier are unaffected; cross-side compatibility is
  proven by the importer's check-mode accepting reviewerId-bearing logs and
  reproducing real-log hashes).

## Provisioning (operator, on the server)

```bash
bun scripts/provision-reviewer.ts provision --name "Ada Teacher" --by "operator:<you>" [--note "..."]
# -> prints the token ONCE; hand it to the reviewer over a secure channel
bun scripts/provision-reviewer.ts list [--all]
```

The action is appended to the append-only provisioning audit log
(`provisioning-log.jsonl`, gitignored, path overridable via
`TV_PROVISIONING_LOG_FILE`): who provisioned whom, when, why.

## Login (reviewer, in the workbench UI)

Paste the provisioned token → `POST /api/session` verifies it against the
registry (constant-time hash compare, active status required) → issues an
HMAC session cookie (HttpOnly, SameSite=Strict, Secure in production, 12h)
whose payload binds `{v:2, reviewerId, name, role, exp, epoch}`. The
display name comes from the REGISTRY — a client-supplied name is ignored
(no impersonation). Tokens are not cached by the browser (no localStorage).

## Why a cookie alone is not authorization

Staging revalidates the reviewer against the registry on EVERY write:
record must exist, be active, and the session epoch must equal the record's
current epoch. Therefore:
- a stolen cookie dies at revocation/re-provisioning (immediate, not at
  12h expiry);
- a cookie cannot mint new identity or change attribution;
- expired/forged/legacy-v1 cookies fail verification fail-closed.

## Revocation

```bash
bun scripts/provision-reviewer.ts revoke --id tvr-xxxxxxxx --by "operator:<you>" [--note "..."]
```

Revocation flips status, bumps `epoch`, and is effective IMMEDIATELY for any
outstanding session. The dead token cannot open a new session either.
Audited in the provisioning log. Re-boarding = provision a new identity
(new id, new token); the old id stays revoked in the audit trail.

## Session-secret rotation (break-glass / key-age policy)

```bash
bun scripts/provision-reviewer.ts rotate-session-secret --by "operator:<you>"
```

Generates a fresh 32-byte secret (0600, fsync'd, tmp+rename) — instantly
invalidating EVERY outstanding session (fail-closed). Reviewers keep their
tokens and simply log in again. Rotating is the response to a suspected
session leak; doing it routinely (e.g. monthly) is recommended before real
teachers arrive.

## Production guarantees (enforced, tested)

- In production the session secret is NEVER auto-generated: missing or
  undersized secret → explicit startup failure (instrumentation gate).
- No hardcoded credentials anywhere in the repo (audited).
- Wrong role / forged / expired / revoked / unknown-token → 403 (test
  matrix in `tests/r3-7/` + adapted R3-6 suite).
